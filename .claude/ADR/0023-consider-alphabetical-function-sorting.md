# ADR 0023: 関数のアルファベット順整列を今後の導入候補にする

- 日付: 2026-11-07
- 状態: 提案中（導入候補として記録。採用・実装・動作検証は未実施）

## 背景

React・TypeScript のファイルに複数の関数がある場合、上から関数名のアルファベット昇順で並べ、目的の関数を探しやすくしたい。自動整列の手段とデメリットを調査し、ユーザーの依頼により今後の導入検討用に記録する。

## 決定と提案

- 今回確定したのは、関数の自動整列を今後の導入候補として保持すること。プロジェクトの必須ルールとしての採用は未決定である。
- 第一候補は `eslint-plugin-perfectionist` の `perfectionist/sort-modules`。`type: "alphabetical"` と `order: "asc"` による名前順の検出・自動修正を検討する。
- 初期の適用案は、独立した関数を集めた utility ファイルや、ファイル直下の関数宣言に限定する。React コンポーネント内部の処理への全面適用は提案に含めない。
- 公開関数・非公開関数をまとめて整列するか、役割ごとに分けるかは導入時に決める。安全上の区切りや依存関係があるため、ファイル全体の完全な A→Z は前提にしない。
- [ADR 0016](0016-simple-import-sort.md) の import・export 整列方針は維持する。候補プラグインの推奨設定を一括で有効化せず、必要なルールだけを追加する案とする。

## 調査内容と未確認事項

- `sort-modules` はモジュールの関数宣言・型・クラスなどを対象とする。関数だけを扱う専用ルールではないため、混在ファイルの配置も確認する必要がある。
- 調査時に参照した公式開発ソースでは、単一の `const` アロー関数宣言を `sortArrowFunctions: true` で対象にできる。公式サイトの取得結果に差があったため、配布版で利用可能なバージョンは未確定である。
- このアロー関数対応は、`memo(() => ...)` などで包まれた関数を対象としない。コンポーネント内部のイベントハンドラーや `useCallback(...)` まで同じ設定で整列できるとは扱わない。
- 公式ドキュメントと開発ソースの調査であり、本リポジトリへのインストール、設定追加、自動修正の実行、挙動の実証は行っていない。開発ブランチの内容を配布済み機能の保証としない。

## 利点と懸念

| 観点 | 期待する利点 | 懸念 |
| --- | --- | --- |
| 探索と配置 | 名前から位置を予測でき、関数の追加場所が一定になる | 主役のコンポーネントや公開 API が途中に埋もれる場合がある |
| 読みやすさ | 同じ接頭辞の関数がまとまる | 呼び出し元と補助関数が離れ、処理の流れを追いにくくなる場合がある |
| 差分 | 継続的に配置を統一できる | 初回の大量移動や関数名変更に伴う移動で、レビュー負担・競合が増える |
| 実行時の挙動 | 安全に移動できる宣言では挙動を維持できる | 初期化・副作用・依存関係の順序を崩すと挙動が変わる |

`const` は初期化前に参照できない。関数定義の順番と、その関数を呼び出す文や初期化式の実行順序を区別する。React では `useCallback` の依存配列などもその場で評価されるため、コンポーネント内部を名前だけで並べ替えない。Hooks の呼び出し位置・順序の制約も保つ。これらは一般的な並べ替えのリスクであり、候補プラグインが特定の不正変換を行うと確認したものではない。

## 代替案

- 現状の手動配置を維持する: 依存関係や処理の流れに合わせやすいが、名前順の統一は自動化できない。
- 役割ごとのグループ内だけを名前順にする: 関連処理のまとまりを保ちやすいが、ファイル全体の完全な昇順にはならない。
- `eslint-plugin-sort-declarations` を使う: モジュール・ブロック内の宣言を扱えるが、独自のグループ分け、依存関係処理、TypeScript・React との適合性を別途検証する必要がある。
- Prettier 単体を使う: 順序変更は対象外のため、今回の自動整列は実現できない。書式整形には引き続き利用できる。

## 導入を判断する際の確認

1. 配布版の対応機能・設定スキーマと、既存の ESLint・TypeScript 環境との互換性を確認する。
2. 対象ファイル、関数の書き方、公開・非公開のグループ、大文字小文字の扱い、対象外にする箇所を決める。
3. 少数の代表ファイルで自動修正の差分を確認する。型・クラス・コメントの移動、初期化順序、既存の import 整列との競合も確認する。
4. 型チェックと既存テストを行い、初回の整列は機能変更と分ける。警告だけにする場合も、`--fix` や保存時修正では変更が適用され得ることを考慮する。
5. 検証結果を踏まえて採否を決め、本 ADR に対象範囲・採用バージョン・検証結果を追記する。

## 結果

今後の検討に必要な候補・利点・懸念・確認事項を保持する。現時点では依存パッケージ、ESLint 設定、ソースコードの配置を変更しない。
