## 元の学習メモ

src/modules/xxx.repository.tsには、ReactからAPIを直接叩く処理をまとめる。
e.g.

- src/modules/auth.repository.ts: 認証関連のロジック
- src/modules/note.repository.ts: ノート関連のロジック

### エンティティ

データベースに保存されるデータの型や構造を定義するためのクラス。
データベースに保存されるような重要なデータは構造が複雑だったりアプリ内で使う箇所も多い。
専用のクラスで型や構造を定義することで取り回ししやすくなる。

e.g. src/modules/users/user.entity.ts

#### エンティティでパスワードを定義しない理由

ユーザーはパスワードのデータもデータベース上は持っている。

パスワードはデータベースに保存はされるが、

- フロント側では使う必要がない
- バックエンドから返ってこない
  - セキュリティの観点からバックエンドからフロントエンドにデータを返す際に意図的に取り除いて返すようにする

### useState

その値を保持しておくためのカスタムフック。
入力されたテキストの内容が同期されるようにするためには以下の設定を行う。

1. 入力するフォームにvalueプロパティとonChangeプロパティを付ける。
1. 該当するonChangeプロパティの中に、`e`と`e.target.value`を指定する。
   - e.g. `onChange = {(e) => setName(e.target.value)}`

データの流れは以下になる。

1. onChangeプロパティでsetNameカスタムフックを呼び出す
1. Constで定義されているname変数に値が代入される。
1. その値をvalueプロパティに入れる。

### ボタン

React.jsでボタンのUI上の制御は`disabled`プロパティで行うことができる。必須にしたい項目のプロパティを感嘆符で指定し、複数ある場合はOR演算子でチェーンさせて判定させる。

入力フォームの`value`プロパティの値に値が入っていなければ`true`になり、値が入っていれば`false`になる。各値の先頭に感嘆符をつけることで、それを逆転させて判定させて制御する。

### AI による補足：元のメモとの対応

- 「API を直接叩く処理をまとめる」という整理は、今回の repository の役割を捉えている。
  「認証関連のロジック」のうち、ここでまとめているのは主に API 通信とレスポンスの変換。
  認証に関するすべての処理が repository に入るわけではない。
- auth repository の実際のパスは `src/modules/auth/auth.repository.ts`。
  note repository は今後の構成例として扱う。
- 「構造が複雑だったりアプリ内で使う箇所も多い」「取り回ししやすくなる」という捉え方は、
  データの構造を共通化する利点。ただし、そのために class が必須というわけではない。
- 今回のフロント側の User は、API から受け取り、画面などで扱うユーザー情報を表す。
  DB の構造全体と同じとは限らない。
- 「パスワードを持っている」という点は、通常は平文ではなくハッシュを DB に保存すると補足できる。
  登録時には入力したパスワードを送信するが、ユーザー情報のレスポンスにパスワードやハッシュを含めない。
- フロント側の型に password を書かないだけでは、実データを取り除けない。
  元のメモにある「バックエンドで意図的に取り除いて返す」という点が重要になる。
- 「その値を保持しておく」という useState の捉え方を起点に、Hook の種類と更新の仕組みを補足する。
  useState は React 組み込みの Hook、setName はそこから返る更新関数で、どちらもこの例ではカスタム Hook ではない。
- 「name 変数に値が代入される」は、その場の const 変数を書き換えるという意味ではない。
  setName が更新を依頼し、次の描画で新しい name を受け取る。詳しい流れは後述の useState の節にまとめる。
- disabled の説明では、文字列そのものと `!文字列` の評価を区別する。
  空文字は真偽値として false、それを `!` で反転すると true。disabled が true のときボタンは無効になる。

### 1. repository における例外処理の役割

**確認の出発点**：Udemy のコース16で repository に例外処理が書かれていない点について、
処理が不要なのか、ほかの場所で対応するのかを確認した。

**AI による補足**

Axios の呼び出しが失敗すると、await の位置で例外が発生し、呼び出し元へ伝わる。
repository に catch がなくても、エラーを無視しているわけではない。
画面側などで受け取り、失敗の表示や送信中状態の解除を行う。

```ts
try {
  const result = await authRepository.signup(name, email, password);
  // 成功後の処理
} catch (error: unknown) {
  // 失敗メッセージを表示する
} finally {
  // 送信中状態を解除する
}
```

repository でエラーをアプリ用の形式に変換する場合には、そこで catch する意味がある。
同じエラーをそのまま投げ直すだけなら、通常は不要。
教材で省略している意図そのものは未確認。

2026-10-26 の整理時点では、[Signup.tsx](../src/pages/Signup.tsx) に登録ボタンから repository を呼ぶコードがある。
一方、signup 関数には try/catch や送信中状態の管理はまだない。
この節のコードは対応方法の例であり、実装済みの処理ではない。

### 2. `!` の読み方・用途と、実行時の挙動

**確認の出発点**：型の近くに付く `!` の読み方や必要性を確認した。
さらに、CRUD の結果が undefined になる問題を防ぐために使えるか、位置による違いも確認した。

**AI による補足**

記号はエクスクラメーションマーク（感嘆符）。置く場所によって意味が異なる。

| 書き方            | 意味                                                            |
| ----------------- | --------------------------------------------------------------- |
| `createdUser!.id` | createdUser は null・undefined ではないと TypeScript に宣言する |
| `createdUser.id!` | id は null・undefined ではないと TypeScript に宣言する          |
| `name!: string`   | name に確実に代入すると TypeScript に宣言する                   |
| `!createdUser.id` | id の真偽値としての評価を反転する                               |

前の2つは non-null assertion、プロパティ宣言のものは definite assignment assertion。
これらの型に関する `!` は実行時には残らず、値の設定・存在確認・待機を行わない。
`createdUser.id!` でも、createdUser 自体が undefined ならアクセス時のエラーは防げない。

```ts
class User {
  name!: string;
}

const user = new User();
console.log(user.name); // 実際には undefined
```

> [!WARNING]
> **厳格な初期化チェックでは、Object.assign による間接的な代入を認識できず、`!` を使う場合がある。
> 2026-10-26 の確認時点の tsconfig.app.json では、その初期化チェックは有効になっていない。**

### 3. CRUD の結果を使うタイミングと undefined の予防

**確認の出発点**：データの取得前に値を使ってしまうケースについて、対処方法と予防方法を確認した。

**AI による補足**

後続の処理が API の戻り値を必要とするなら await で待つ。

```ts
const { user: createdUser } = await authRepository.signup(
  name,
  email,
  password,
);
console.log(createdUser.id);
```

await は完了を待つだけで、戻り値が必ず存在することまでは保証しない。
undefined の原因は、待機不足以外にも return の書き忘れ、レスポンス構造の参照間違いなどがある。
削除 API のように、成功時に本文がない仕様もある。

| 目的                                                     | 方法                |
| -------------------------------------------------------- | ------------------- |
| 非同期処理を待つ                                         | await               |
| 存在する場合だけ処理する                                 | if による確認       |
| null・undefined のときに代替値を使う                     | `value ?? "代替値"` |
| null・undefined のときにプロパティへのアクセスを短絡する | `user?.id`          |

React の setState は、その場の state 変数を書き換える処理ではない。
取得直後に値を使うなら、state ではなく API の戻り値を使う。

```tsx
const result = await authRepository.signup(name, email, password);
setUser(result.user);
console.log(result.user.id);
```

画面では読み込み中・取得失敗・データなし・取得成功を区別する。
複数の取得が競合し、古い応答が新しい表示を上書きする場合には、通信の中断や古い結果の無視なども必要。

### 4. constructor と this の役割

**確認の出発点**：constructor は JavaScript の予約語なのか、何をするものかを確認した。

**AI による補足**

constructor は、クラス内で特別な意味を持つメソッド名。
どこでも変数名として使えない予約語という意味ではない。
new でインスタンスを作るときに初期化を行い、ここでの this は作っているインスタンス自身を指す。

```ts
class User {
  name: string;

  constructor(name: string) {
    this.name = name;
  }
}

const user = new User("田中");
console.log(user.name); // "田中"
```

### 5. Object.assign のコピー先・コピー元

**確認の出発点**：教材の「第1引数がコピー先、第2引数がコピー元」という説明を、
`Object.assign(this, data)` に当てはめて確認した。

**AI による補足**

元のメモにある説明は、「data の各項目を、今作っているインスタンスに代入する」と読み替えられる。

```ts
Object.assign(this, data);

// data が以下の3項目のみなら、おおむね次の代入に対応する
this.id = data.id;
this.email = data.email;
this.name = data.name;
```

コピー先を書き換え、同名の項目は上書きする。
クラスで宣言した項目だけを選ぶ機能ではなく、data に余分な項目があればそれもコピーする。
また、浅いコピーなので、ネストしたオブジェクトの内部まで独立した複製にはならない。

### 6. エンティティに class を使う理由と、type という選択肢

**確認の出発点**：教材の「データに関する処理もまとめるため class を使う」という説明を確認した。
名前が空ならダミーの名前を返す、という教材の例を基に整理する。

**AI による補足**

データの構造だけなら type・interface でもよい。
class ではデータと、それに基づく処理を同じ場所にまとめられる。

```ts
type UserData = {
  name: string;
};

class User {
  name: string;

  constructor(data: UserData) {
    this.name = data.name;
  }

  getDisplayName(): string {
    return this.name.trim() || "名前未設定";
  }
}
```

同じ処理を `getDisplayName(user)` という独立した関数にする方法もある。
React・TypeScript でユーザーデータを必ず class にする決まりはない。

2026-10-26 に確認した repository の `new User(user)` は、API から受け取った通常のオブジェクトを基にインスタンスを作る処理。
型の指定やインスタンス化だけでは、API の実データを検証したことにはならない。

### 7. useState と入力欄の値の更新

**確認の出発点**：元メモの「その値を保持しておく」「入力されたテキストの内容が同期される」という整理を基に、
`e.target.value` の意味と、入力から画面更新までの流れを確認する。

**AI による補足**

以下は Signup.tsx と同じ構成を使った説明用の抜粋。

```tsx
const [name, setName] = useState("");

<input
  value={name}
  onChange={(e) => setName(e.target.value)}
/>
```

| 記述 | 役割 |
| --- | --- |
| `useState("")` | 初期値を空文字にして state を用意する React 組み込みの Hook |
| `name` | この描画での state の値 |
| `setName` | 次の state の値を指定する更新関数 |
| `value={name}` | state の値を入力欄に表示する |
| `onChange` | 入力内容が変わったときに実行する処理 |
| `e` | React からイベントハンドラーに渡されるイベント。引数名は自由 |
| `e.target` | イベントが発生した要素。この例では input |
| `e.target.value` | この入力欄に入っている文字列 |

流れは「入力 → onChange → setName に文字列を渡す → 次の描画で新しい name を受け取る → value に反映」。
このように React の state で値を管理する入力欄を controlled input と呼ぶ。
`const name` を直接再代入する処理ではない。[React: useState](https://react.dev/reference/react/useState)、[React: input](https://react.dev/reference/react-dom/components/input)

元のメモにある「カスタムフック」は、この例では「組み込み Hook」と「更新関数」に分けて読む。
カスタム Hook は、Hook を使う処理を自分でまとめて再利用するための関数を指す。
state 更新直後に古い値が見える点は、前述の「CRUD の結果を使うタイミング」で扱ったとおり。

#### 入力欄ごとに e.target.value を取得できる仕組み

**確認の出発点**：セッションで、e.target.value がなぜ email や password の入力欄を識別できるのかを追加で確認した。

**AI による補足**

e.target.value 自体が email・password という名前を判別しているわけではない。
それぞれの入力欄に onChange が設定されており、変更が起きた入力欄のイベントが、その処理に渡される。

```tsx
<input
  value={email}
  onChange={(e) => setEmail(e.target.value)}
/>

<input
  value={password}
  onChange={(e) => setPassword(e.target.value)}
/>
```

メールアドレス欄に入力すると、その欄の onChange が実行され、e.target はその input を指す。
e.target.value はその欄の文字列で、setEmail が保存先の state を決める。
パスワード欄では、その欄に設定した setPassword の処理が実行される。

| 役割 | 決めているもの |
| --- | --- |
| どの入力欄の値を読むか | この例では、変更イベントの発生元である e.target |
| どの state を更新するか | 自分でハンドラーに書いた setEmail・setPassword |
| state の値をどこに表示するか | 各入力欄の value={email}・value={password} |

この書き方では、id や name 属性から保存先の state を自動的に選んでいるわけではない。
仮にメールアドレス欄のハンドラーを `setPassword(e.target.value)` にすると、入力した文字列は password の state に渡される。
email は更新されず、value={email} で管理されるメールアドレス欄も意図どおりに更新されなくなる。

### 8. disabled と先頭の `!` による空欄判定

**確認の出発点**：元メモの「disabled プロパティ」「OR 演算子でチェーンさせて判定」を、
実際の式に当てはめて整理する。

**AI による補足**

2026-10-26 の Signup.tsx は、次の式で登録ボタンを制御している。

```tsx
disabled={!name || !email || !password}
```

先頭の `!` は論理否定。今回の3つの state は文字列なので、次のように評価される。

| 値の例 | 真偽値としての評価 | `!値` |
| --- | --- | --- |
| `""` | false | true |
| `"田中"` | true | false |
| `"   "` | true | false |

`||` は、この式ではどれか1つでも true なら全体が true になる。
つまり「どれかが空欄なら disabled=true、すべて空欄でなければ disabled=false」となる。
元メモの「値が入っていなければ true」は、値そのものではなく、`!name` などに反転した後の評価として読める。

これは空文字の確認であり、メール形式やパスワード条件、送信中かどうかまで検証するものではない。
空白だけの入力も空文字とは異なるため、必要な検証は別に設計する。
型の後ろに付ける `!` との違いは、前述の比較表を参照する。

## セッションで追加確認したテーマ（AI による補足）

### console.log の文字列連結とオブジェクト表示

**確認の出発点**：セッションでは、`console.log("user:" + user)` が `user:[object Object]` と表示され、
`console.log(user)` ではプロパティを確認できる理由を確認した。

**AI による補足**

```js
console.log("user:" + user); // 今回の User では user:[object Object]
console.log(user);          // オブジェクトを渡す
console.log("user:", user); // ラベルとオブジェクトを別々の引数として渡す
```

1行目は `+` で文字列を連結するため、user が文字列に変換される。
今回の User は独自の文字列変換を定義しておらず、結果は通常の `[object Object]` になる。
console.log に届く時点では、すでに1つの文字列になっている。
2・3行目はオブジェクトをそのまま渡すので、ブラウザの開発者ツールがプロパティを展開できる形で表示する。

```js
console.log(`user: ${user}`); // テンプレートリテラルでも文字列への変換が起こる
```

ログの先頭の User はクラスのインスタンスであることを示す表示。
実際にどのように表示されるかは開発者ツールによる。[MDN: console.log](https://developer.mozilla.org/en-US/docs/Web/API/console/log_static)、[MDN: Addition](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Addition)

提示されたログには、クラスで宣言していない createdAt・updatedAt も含まれていた。
これは前述の Object.assign の注意点とつながる。型に書いた項目だけに実行時のオブジェクトが制限されるわけではない。

### HTTP クライアントの選択

Fetch API は Web 標準の通信 API、Axios は汎用 HTTP クライアント、Ky・ofetch は Fetch API を便利に扱うためのライブラリ。
Axios は Fetch API が広く普及する前から存在し、XHR などによる通信を扱いやすくしてきた。
完全な上位互換という関係ではなく、設定や戻り値、エラーの形が異なる。
以下の使い分けは、このセッションでの AI による選択の目安であり、公式に定められた順位ではない。

Fetch API は HTTP 400・500 が返っただけでは例外にならないため、自分で確認する。

```ts
const response = await fetch(url);
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
const data = await response.json();
```

| 状況                                        | 選択の目安                                        |
| ------------------------------------------- | ------------------------------------------------- |
| React で API 呼び出しが少ない               | Fetch API と小さな共通関数                        |
| JSON 処理や時間制限、共通処理などを整えたい | Ky・ofetch を検討                                 |
| Axios の既存実装やチームの経験がある        | 継続する合理性がある                              |
| Next.js のサーバーで HTTP API を直接呼ぶ    | キャッシュ・再検証を扱える Fetch API を基本に検討 |
| Next.js のブラウザで呼ぶ                    | React SPA と同じ基準で検討                        |

ライブラリは定型処理を減らせる一方、独自仕様や更新への対応が必要になる。
Next.js のキャッシュ動作はバージョンと設定にも依存する。
TanStack Query は取得状態やキャッシュを管理する別の層で、通信手段と組み合わせて使う。
複数の層でのリトライや、登録処理の重複実行には注意する。

### Stripe・Google カレンダーでは公式 SDK も検討する

外部サービスでは、汎用クライアントの比較に加え、公式 SDK が必要な機能・認証・実行環境に合うかを確認する。

- Stripe: サーバー側では stripe SDK。ブラウザでは決済方式に応じて Stripe.js・React Stripe.js。
  サーバー用の秘密のキーはブラウザに渡さない。
- Google カレンダー: 継続同期が必要なら、サーバー側で OAuth とトークンを管理し、googleapis の利用を検討する。
  画面を開いている間だけの利用なら、ブラウザで認可を受けてアクセスする構成も候補になる。

ブラウザから自分のサーバーへは Fetch API・Ky など、サーバーから外部サービスへは SDK、という併用ができる。
SDK を使っても、権限・トークンの保存・業務上のエラー対応などはアプリ側で設計する。

### lint・build とコミットの違い

**確認の出発点**：コミット後の報告にあった「全体の lint・build は既存エラーで失敗」の意味を確認した。

**AI による補足**

lint はコードのルール違反などを検査し、build は配布用の成果物を作るための処理。
このリポジトリの build は `tsc -b && vite build` なので、TypeScript のチェックが失敗すると Vite には進まない。
Git のコミットは変更を履歴に保存する操作であり、lint・build とは別の処理である。
コミットの成功だけでは、アプリ全体が検証に成功したことにはならない。

このセッションで実行した検証では、全体の lint は既存ファイルの11 errors・4 warnings、
build は NoteItem.tsx の未使用 import 2件で失敗した。
変更した Signup.tsx・auth.repository.ts・user.entity.ts の個別 lint は成功したが、
アプリ全体の build 成功やバックエンドとの実通信を確認したわけではない。
これは当該検証時の結果であり、今回の復習版生成では再実行していない。
