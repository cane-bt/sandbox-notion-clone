## 確認したこと・理解の整理

**確認の出発点**

- CSS の相対パス以外に、配置変更へ対応しやすい書き方があるか。
- アロー関数とオブジェクトのメソッドの違い、関数を渡すことと実行することの違い。
- `/auth/me` が Axios の標準機能なのか、別途バックエンドが必要なのか。
- interceptor の `config` と `headers`、Bearer `token` の意味。
- `useEffect` の依存配列と実行タイミング、読み込み状態によって `return` が切り替わる理由。
- `const` の間に `useEffect` がある配置への違和感と、React Compiler の自動最適化の対象。

### 講座22: `token` の保存

**AI による補足**

- 登録・ログイン API が返す `token` を `localStorage.setItem("token", token)` で保存する。
- フォームは保存後に共有ユーザーを更新し、送信中のボタン無効化と失敗アラートを扱う。
- 保存だけでは API に `token` は送られない。`localStorage` は JavaScript から読み取れるため、HttpOnly Cookie と同じ保護ではない。

### 講座23: `token` 付きユーザー取得

**AI による補足**

- request interceptor は送信前の共通処理。関数をフォルダーに置くだけでは動かず、`api.interceptors.request.use(addAuthorizationHeader)` で登録する。
- `config` は Axios がまとめた通信設定。`url`・`method`・`baseURL`・`data`・`headers` などを持つ。`InternalAxiosRequestConfig` は `headers` が必須の型。
- 共通設定の `Content-Type` と Axios 標準の `Accept` に、`token` があれば `Authorization: Bearer` を追加する。`token` がなくても通信は継続する。
- Bearer はトークン提示の方式。ユーザー用に限らずサービス用のアクセストークンなどにも使われ、JWT と同義ではない。
- `/auth/me` はアプリ側の API パスであり、Axios が用意するユーザー取得機能ではない。本リポジトリには受け側の実装がなく、別バックエンドの仕様確認が必要。

### 講座24: 起動時復元と `useEffect`

**AI による補足**

- `useEffect` の行では関数を React に渡し、中身は DOM への反映後に実行される。コード上の位置で通信が即時実行されるわけではない。
- 最初は `useState(true)` により `isLoading` が `true` なので、読み込み中の JSX を `return` する。その回の `App` の実行は終了する。
- 通信完了後の `setIsLoading(false)` が再描画を要求する。`App` が最初から再実行され、今度は `false` なので通常画面の JSX を返す。`return` の位置で処理を待って再開するわけではない。
- `useState` の初期値は通常の再描画で状態を `true` に戻すものではない。`finally` で `false` にするため、成功と失敗のどちらでも読み込みは終わる。
- 依存配列は Effect が使う値から決める。取得関数を Effect 内へ移し、`setCurrentUser` を依存に含める。cleanup 後は古い結果を無視する。通信のキャンセルとは別。
- `StrictMode` の開発時は追加の Effect 実行がある。`[]` はアプリの生涯で絶対に1回だけという保証ではない。
- Hook は条件分岐・早期 `return` より前で毎回同じ順序で呼ぶ。`const` を必ずファイル上部に集めるという規則はない。
- React Compiler が主に自動化するのは `useMemo`・`useCallback`・`memo` 相当のメモ化。`useEffect` や cleanup を不要にするものではない。現リポジトリには Compiler の明示的な導入設定なし。
- Effect に直接通信を書く基本形を学んだ後、カスタム Hook や取得ライブラリで整理できる。長い Effect を毎回書くこと自体が理想ではない。

### アロー関数・メソッドと、関数を渡すこと

**確認の出発点**

`Signin.tsx` の `const signin = async () => { ... }` と、repository の `async signin(...) { ... }` の違い、および `onClick={signin}` でその場では実行しないという説明を確認したかった。

**AI による補足**

前者はアロー関数を変数へ代入し、後者はオブジェクトのメソッドを定義している。どちらも関数であり、画面用と API 用で構文が必須とされているわけではない。画面側は外側の `email`・`password` を参照するクロージャを使い、repository は引数で受け取る。アロー関数とメソッドには `this` の扱いなどの違いがあるが、今回の処理では `this` を使っていない。

| 書き方 | 意味 |
| --- | --- |
| `signin` | 関数そのもの。引数や props として渡せる |
| `signin()` | 関数を今呼び出し、戻り値を得る |
| `onClick={signin}` | React に関数を渡し、クリック時に呼んでもらう |
| `onClick={() => signin()}` | 呼ばれたら signin を実行する別の関数を渡す |
| `use(addAuthorizationHeader)` | Axios に関数を渡し、リクエスト送信前に呼んでもらう |

`onClick={signin()}` はレンダー中に実行し、その戻り値を渡してしまう。関数を渡して後から呼んでもらう形をコールバックという。React はクリックイベント、Axios は `config` を引数として用意する。

### `App` の再実行と Effect が実行されるタイミング

**確認の出発点**

本人は `if (isLoading)` によって読み込み表示から通常画面へ切り替わる理由と、`return` より上にある `useEffect` がいつ動くのかを確認したかった。

**AI による補足**

React のレンダーはコンポーネント関数を呼んで表示内容を計算する段階、コミットは DOM へ反映する段階。ブラウザーがピクセルを描く段階とは区別する。以下の「DOM 反映後」は、必ず文字が目に見えてから通信が始まるという保証ではない。

```text
最初の App 実行（isLoading は true）
  → useEffect に関数を渡す。この時点では中身を実行しない
  → 初期コードでは、この後に fetchCurrentUser 関数を定義する
  → 読み込み中の JSX を return して、この回の App 実行は終了
  → React が DOM に反映
  → 渡された Effect の関数を実行し、API 通信を開始
  → 通信完了後、setIsLoading(false)
  → React が App を最初から再実行
  → 今度は if を通過し、通常画面の JSX を return
```

初期コードが後で定義する関数を呼べたのは、Effect の中身の実行時には宣言が済んでいたため。ただし依存関係の問題と lint の指摘は別に残るため、現在は取得関数を Effect 内へ移している。通常の再描画で `useEffect` の行に到達することと、Effect の中身が再実行されることも別である。

### 依存配列・配置・改善コードの位置付け

**確認の出発点**

> `const`は基本的に上の方で、コンポーネントもしくはそのファイルの中の上部の方で基本的に設定されるはずなのに、`useEffect`は複数の`const`の間に入っているということが気持ち悪いです。

これは本人の配置に関する着眼点であり、Hook の正しさの判定と分けて考える。

**AI による補足**

| 依存配列 | 動作 |
| --- | --- |
| 第2引数なし | 各コミット後に実行 |
| `[]` | マウント時に実行。通常の再描画ではやり直さない |
| `[value]` | マウント時と、value が変わったコミット後に実行 |

配列は実行回数を好きに選ぶ指定ではなく、Effect 内で参照するリアクティブな値に合わせる。依存する値を省くと古い値を使い続ける場合がある。コンポーネント内の関数を依存へ足すだけでは、再描画のたびの参照変化で不要な再実行が起き得る。今回 Effect 内へ関数を移したのは、この依存を整理するためである。

`const` と Effect を必ず交互に並べる必要も、`const` をすべてファイル上部へ集める規則もない。読みやすい順序にできるが、Hook は条件分岐・ループ・早期 `return` を挟まず毎回同じ順で呼ぶ。コード上の配置を移しても、Effect の実行タイミングを即時呼び出しへ変えるものではない。

今回の改善例は、直接 Effect でデータ取得する場合の基本形で、常に最善の設計という意味ではない。カスタム Hook で整理したり、取得ライブラリにキャッシュ・再取得等を任せたりできる。React Compiler のメモ化は Effect の依存関係や cleanup の誤りを自動修正するものではない。

### `void` `fetchCurrentUser` の意味

**確認の出発点**

本人は `void fetchCurrentUser();` の `void` が何をするのかを確認したかった。

**AI による補足**

```ts
void fetchCurrentUser();
//   関数は実行する。返された Promise はここでは使わない。
```

`async` 関数は明示的な `return` がなくても `Promise` を返す。`void` 演算子は式を実行し、その式の結果を `undefined` にする。ここでは、呼び出し側で `Promise` の完了を待たず、戻り値を使わない意図を示している。

| 書き方 | 呼び出し側で待つか |
| --- | --- |
| `await fetchCurrentUser()` | 待つ |
| `fetchCurrentUser()` | 待たない |
| `void fetchCurrentUser()` | 待たず、戻り値を使わないと明示する |

`void` は通信や関数内の `await` を止めず、エラーも処理しない。現在は関数内の `try/catch` が API の失敗を扱う。戻り値の型としての `: void` とは別の使い方。Effect の関数自体は `Promise` ではなく cleanup 関数または何も返さない形にするため、中の取得関数を `async` にしている。

### cleanup と「`App` が画面から外れる」の意味

**確認の出発点**

> 「`App` が画面から外れるときに」の意味が分からない

本人は cleanup 関数を返す意味と、`ignore` が `true` になるタイミングを確認したかった。

**AI による補足**

「画面から外れる」は、React がコンポーネントを表示構成から取り除くアンマウントを指す。ウィンドウ最小化や別タブへの切り替えではない。現在は `App` の内側で `Signin` や `Home` が切り替わるため、通常のルート移動だけでは `App` はアンマウントされない。ブラウザー終了時に必ず cleanup が実行されるという保証もない。

説明用に親が `showApp ? <App /> : <OtherScreen />` としていれば、`showApp` が `false` になると `App` が外れる。ただし現在の実装にこの条件分岐があるわけではない。

```tsx
// 仕組みを示す抜粋。実コードは catch・finally にも ignore の確認を持つ。
useEffect(() => {
  let ignore = false;

  const fetchCurrentUser = async () => {
    const user = await authRepository.getCurrentUser();
    if (!ignore) {
      setCurrentUser(user);
    }
  };

  void fetchCurrentUser();

  return () => {
    ignore = true;
  };
}, [setCurrentUser]);
```

この `return` は Effect の関数から後片付け用の関数を React に返す。`App` から JSX を返す `return` とは別で、その場で `ignore = true` を実行するわけではない。

React は依存変更による Effect の再実行前、アンマウント時、開発時 `StrictMode` の追加確認で cleanup を呼ぶ。`await` で通信を待っている間にも cleanup は呼ばれ得る。後で通信が完了すると、その実行に対応する `ignore` の値を確認する。

| 時系列 | 古い実行A | 新しい実行B |
| --- | --- | --- |
| A開始 | `ignore` は `false`、通信Aを開始 | まだない |
| cleanup A | `ignore` を `true` にする | まだない |
| B開始 | A用の `ignore` は `true` のまま | 別の `ignore` を `false` で作り、通信Bを開始 |
| 応答到着 | Aの結果は反映しない | cleanup 前ならBの結果を反映する |

`ignore` は全通信で共有する一つの変数ではなく、Effect の実行ごとに作られる。通信Aそのものは続き、サーバーへ届く場合もある。この対策は通信の中止や重複排除ではなく、不要になった実行が後から状態を書き換えるのを防ぐもの。
