## 確認したこと・理解の整理

### API のレスポンスと日時の変換

**確認の出発点**

講座の「API から返ってきた情報」が、フロントエンドから送るデータなのか、バックエンドから取得するデータなのかを確認した。本人の説明による講座の表現であり、教材本文は未確認。

**セッション中の本人の整理（質問時点）**

> この講座では、React.jsから受け取ったデータを初期化して、バックエンドに届けるときにコンストラクターを通して、日時の文字列をデート型に変更するという認識なのですが、それは合ってますか？

**AI による補足**

日時の文字列を `Date` オブジェクトに変換する点は合っているが、今回のコードが扱う向きはバックエンドからフロントエンドへのレスポンス。JSON には日時専用の型がなく、日時は通常文字列で届く。型注釈だけで実際の値が変換されるわけではない。

整理時点の [ノート作成処理](../src/modules/notes/note.repository.ts) では、次の順序になっている。

```text
React 側で noteRepository.create(params) を呼ぶ
  → POST /notes で title・parentId をバックエンドへ送る
  → バックエンドからレスポンスを受け取る
  → new Note(result.data) にレスポンスを渡す
  → createdAt の文字列を Date オブジェクトに変換する
```

[Note クラス](../src/modules/notes/note.entity.ts) のコンストラクターは次の処理を行う。

```ts
constructor(data: Note) {
  Object.assign(this, data);
  this.createdAt = new Date(data.createdAt);
}
```

- `Object.assign(this, data)` は受け取ったプロパティを作成中のインスタンスにコピーする。
- `new Date(data.createdAt)` は日時の値を `Date` オブジェクトに変換し、`createdAt` を上書きする。
- 実際のプロパティ名は `createdAt`。質問中の `created_at` とは異なり、名前の自動変換はこのコンストラクターにはない。
- `createdAt` は作成日時という値の意味を表す名前で、送受信の方向を示すものではない。バックエンドでの日時の生成方法は今回未確認。

最初の回答時には `new Note(...)` の呼び出しがなかったが、2026-11-03 の整理時点では `noteRepository.create()` に存在する。現在の実装説明には後者を採用した。HTTP 通信の成功や画面との接続は今回動作確認していない。

`constructor(data: Note)` の引数型は `createdAt` を `Date` として宣言している一方、コメントと変換処理は文字列の受信を想定している。API レスポンス用の型を別に持ち、`createdAt: string` と表す方法もある。これは AI の改善案であり、アプリのコードは変更していない。

### nullable・省略可能なプロパティ・空文字

**確認の出発点**

講座で出てきた nullable の意味とコード例を確認した。

**AI による補足**

nullable は値として `null` を許すこと。`?` はプロパティの省略を許す記法であり、両者は別の意味を持つ。次の表は `strictNullChecks: true` を前提とした型の読み方。

| 宣言 | 意味 |
| --- | --- |
| `title: string` | プロパティが必要で、値は文字列 |
| `title: string \| null` | プロパティが必要で、文字列または `null` |
| `title?: string` | プロパティを省略できる。読み出すと `undefined` の可能性がある |
| `title?: string \| null` | 省略でき、値に `null` も使える |

説明用の例（アプリへの追加コードではない）:

```ts
type NoteData = {
  title?: string | null;
};

const a: NoteData = { title: "買い物メモ" };
const b: NoteData = { title: null };
const c: NoteData = {};

// a.title は "買い物メモ"
// b.title は null
// c.title は undefined
```

`null` は値がないことを明示する値。`undefined` は省略したプロパティの読み出しなどで得られるが、明示的な値として存在する場合もあり、「必ずプロパティが存在しない」という意味ではない。`exactOptionalPropertyTypes` を有効にすると、省略と明示的な `undefined` の代入の区別が厳密になる。

```ts
const displayTitle = note.title ?? "無題";
```

`??` は左側が `null` または `undefined` の場合に右側を使う。空文字 `""` は文字列なので、そのまま残る。

会話中に説明した「`string` に `null` を代入すると型エラー」は厳密な null チェックを有効にした場合の説明。2026-11-03 の [tsconfig.app.json](../tsconfig.app.json) には `strict`・`strictNullChecks` と継承元の指定がなく、このプロジェクトではそのチェックは有効になっていない。同じコードを書けば必ず型エラーになると考えないこと。

TypeScript の `| null` は型の宣言であり、データベースの nullable 制約とは別。型を書いてもデータベースの設定やバックエンドの入力検証は変わらず、値を自動的に `null` に初期化することもない。

### VS Code の補完候補に使用履歴を反映する

本人は、数文字入力したときによく使う候補を優先したいと質問した。

```json
"editor.suggestSelection": "recentlyUsedByPrefix"
```

この設定は、入力した文字列ごとに以前選んだ候補を記憶し、あらかじめ選択する。たとえば `co` から `console` を選ぶと、次回の `co` でもそれを選択する。使用回数順に一覧全体を並べ替える設定ではない。

| 設定値 | 選択方法 |
| --- | --- |
| `first` | 常に一覧の先頭 |
| `recentlyUsed` | 最近使った候補を考慮 |
| `recentlyUsedByPrefix` | 入力した文字列ごとの選択履歴を考慮 |

Mac では `Command + ,` で設定を開き、`editor.suggestSelection` を検索して変更できる。2026-11-03 の調査時点では、ローカルの `.vscode/settings.json` に `recentlyUsedByPrefix` が設定されていた。AI が設定を変更したものではない。

メリットは矢印キーによる候補選択が減ること。デメリットは選択位置が履歴で変わり、確認せず確定すると意図しない候補が入る可能性があること。

### macOS と VS Code の標準キー操作

本人は `Ctrl + E`・`Ctrl + P`・`Ctrl + N` が矢印キーと同じ動作なのか、標準設定か独自設定かを確認した。

| キー | テキスト編集中の基本動作 |
| --- | --- |
| `Ctrl + P` | 1行上へ移動 |
| `Ctrl + N` | 1行下へ移動 |
| `Ctrl + B` | 1文字左へ移動 |
| `Ctrl + F` | 1文字右へ移動 |
| `Ctrl + A` | 行頭へ移動 |
| `Ctrl + E` | 行末へ移動 |

これらは macOS の標準テキスト編集操作で、macOS 版 VS Code にも標準の割り当てがある。`Ctrl + E` は右矢印1回とは異なる。`Ctrl`（⌃）と `Command`（⌘）も別のキー。

通常の VS Code ユーザー設定先には `keybindings.json` がなく、`~/Library/KeyBindings/DefaultKeyBinding.dict` も存在しなかった。ただし、後続調査で物理キーを Ctrl に変える Karabiner の独自設定が確認された。VS Code の標準割り当てと、物理キーの変換は別の層として考える。

補完候補では候補の選択、ターミナルでは履歴移動になるなど、フォーカスによって動作が変わる。VS Code の割り当ては `Command + K`、続けて `Command + S` で確認できる。実際の入力と実行コマンドを追う場合は、コマンドパレットから `Developer: Toggle Keyboard Shortcuts Troubleshooting` を使う。

### Caps Lock を Ctrl にする設定と200ミリ秒の待ち時間

**確認の出発点**

本人は、特に補完候補の表示中に `Ctrl + N`・`Ctrl + P` が長押ししないと反応しない、押し続けても動かない場合があると相談した。普段 Ctrl として押している物理キーは「Caps Lock キーの位置」と明示した。

**AI による補足：最初の調査結果**

2026-11-03 の最初の調査時点で、`~/.config/karabiner/karabiner.json` の選択中プロファイルに次のルールがあった。

- ルール名: `Neruのハイパーキーのショートカットキーバインド (caps_lock)`
- 単独の短押し: `Command + Shift + Space`
- 長押し: `to_if_held_down` で `left_control` を出力
- 長押し判定: `basic.to_if_held_down_threshold_milliseconds: 200`

つまり、Caps Lock を押した瞬間には Ctrl が出力されず、200ミリ秒待つ。先に `N` や `P` を押すと、Ctrl より先に文字キーが送られる可能性がある。これが症状と一致する有力な原因。補完候補が再検索されるなどの見え方については推測であり、入力ログを使った再現確認はしていない。

インストール済み VS Code の実装では、補完候補の上下選択に `Ctrl + N`・`Ctrl + P` が登録され、長押しの要求はなかった。保存済み macOS 設定でもスローキーは無効だった。

**AI の設定案と、その後の確認結果**

Karabiner-Elements の `Complex Modifications` で該当ルールを探し、`Edit` で編集する案を案内した。AI の提案は、`to_if_held_down` の代わりに次の `to` を使い、既存の `to_if_alone` を残す構成。

```json
"to": [
  {
    "key_code": "left_control",
    "lazy": true
  }
]
```

`lazy: true` は、別のキーと組み合わせた時点で Ctrl を送る指定であり、一定時間待つ設定ではない。単独の短押しを残しながら素早い組み合わせに対応するための AI の提案。

今回の TIL 整理時点では、実際の設定はすでに `to_if_held_down` から `to` に変更され、`left_control` と `repeat: true` が指定されていた。`lazy: true` はなかった。長押し判定の数値は残っているが、このルールに `to_if_held_down` は存在しない。変更の実施者は断定せず、AI の提案と実際の設定を区別する。反応速度の改善や単独短押しの動作は未確認。
