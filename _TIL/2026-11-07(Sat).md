## 確認したこと・理解の整理

### `App` と `Layout` の非同期取得で共通する処理

**確認の出発点**

`Layout.tsx` のノート取得にも、`App.tsx` のユーザー取得と同じ対策が必要か。本人が書いた Effect の問題点を確認した。

**AI による補足**

どちらも、通信を待った後に状態を更新する処理である。Effect 内に取得関数を定義し、失敗を `catch` で扱い、`finally` で読み込みを終了する。不要になった結果を反映しないため、状態更新前に `ignore` を確認する。

ただし、ユーザー状態とノート一覧では型と更新方法が異なる。`App` のユーザー状態には `undefined` を設定できるが、store の `set` は `Note[]` を受け取る。会話途中の `set(undefined)` は型エラーだった。さらに、既存の `set` はノートを置き換えるのではなく結合するので、`set([])` でも一覧は消えない。

`Layout` では、Effect 内の `if (!currentUser) return;` で未ログイン時の取得を止める。画面側で `<Navigate>` を返すだけでは、登録済みの Effect が通信しない保証にはならない。これは不要な通信を避けるためであり、API の認証・認可はサーバー側で必要である。

### 分割代入と `setNotes` という名前

**確認の出発点**

`const noteStore = useNoteStore();` を変更した理由と、`set: setNotes` の意味を確認した。

**AI による補足**

`useNoteStore()` は `{ getAll, set }` というオブジェクトを返す。次の2つは、関数を取り出すという点で同じ意味である。

```ts
const noteStore = useNoteStore();
const setNotes = noteStore.set;
```

```ts
const { set: setNotes } = useNoteStore();
```

`set` は取り出すプロパティ名、`setNotes` は取り出した値に付ける変数名。関数を実行する構文ではない。分割代入だけで関数の参照が安定するわけでもない。

依存配列の `[noteStore]` はオブジェクト全体、`[noteStore.set]` はその関数を比較する。分割代入後の `[setNotes]` も同じ関数を比較する。初回整理時のコードコメントにあった「noteStore.setだとオブジェクト全体を受け取る」は不正確で、オブジェクト全体を依存にするのは `[noteStore]` の場合である。初回整理では訂正理由のみ示した。後続の公開準備で、アプリのコメントも訂正した。

同名でも、store 内の `setNotes` は `useAtom` から受け取った更新関数で、`Layout` 内の `setNotes` は store の `set` の別名である。別々の場所の変数として読む。

### cleanup を渡す時点と実行される時点

**確認の出発点**

`return () => { ... }` のどこが cleanup なのか、いつ実行されるのか、なぜ `await` の後に `ignore` が変わっている可能性があるのかを確認した。

**AI による補足**

Effect が返す「後片付け用の関数」を cleanup と呼ぶ。次の2つは同じ意味である。

```tsx
return () => {
  ignore = true;
};
```

```tsx
const cleanup = () => {
  ignore = true;
};
return cleanup;
```

`return cleanup;` は関数を React に渡すだけで、その場で実行しない。`cleanup();` と書いた場合が関数の実行である。React は渡された関数を覚えておき、コンポーネントが取り除かれるとき、または依存変更に伴う次の Effect の実行前に呼び出す。通信完了を理由に呼び出すものではなく、依存が変わらない通常の再描画だけでも呼び出さない。開発時の StrictMode では追加の setup → cleanup → setup が行われる場合がある。

次は仕組みを絞った説明用の例であり、エラー処理等を含むアプリ全体の置換コードではない。

```tsx
useEffect(() => {
  if (!currentUser) return;
  let ignore = false;

  const fetchNotes = async () => {
    const notes = await noteRepository.find();
    if (!ignore) {
      setNotes(notes);
    }
  };

  void fetchNotes();

  return () => {
    ignore = true;
  };
}, [currentUser, setNotes]);
```

`await` は `fetchNotes` の続きを待たせる。ブラウザーの操作や React の処理全体を止めない。そのため次の順番が起こり得る。

```text
通信開始 → fetchNotes は await で待つ
→ Effect は cleanup 関数を React に渡して終了
→ 通信中に Layout が取り除かれる
→ React が cleanup を実行し、ignore = true
→ 通信完了後に fetchNotes が再開
→ if (!ignore) が false なので状態を更新しない
```

cleanup と取得関数は、同じ Effect の実行で作った同じ変数を参照する。このように外側の変数を関数から参照できる仕組みが closure である。Effect をやり直すときは、新しい実行に別の `ignore` が作られる。古い実行の `ignore` は `true`、新しい実行のものは `false` として区別される。

### cleanup があっても `if` が必要な理由

**確認の出発点**

cleanup が済んでいるなら、通信後に `if (!ignore)` を書く必要があるのかを確認した。

**AI による補足**

今回の cleanup は `ignore = true` を実行するだけで、通信や取得関数を自動停止しない。後から `setNotes(notes)` を無条件で実行すれば、不要な結果でも反映される。

| コード | 役割 |
| --- | --- |
| cleanup 内の `ignore = true` | この実行の結果が不要になったと記録する |
| 通信後の `if (!ignore)` | 記録を確認し、結果を反映してよいか判断する |

結果を使わない目印と、その目印を見る処理の両方が必要である。取得結果だけでなく、エラー表示や `setIsLoading(false)` も確認する。古い通信の完了で、新しい通信の読み込み表示を終了させないためでもある。

通信自体を中止するには `AbortController` 等を使い、API 呼び出しにもキャンセルを渡す別の実装が必要になる。`ignore` はリクエストの重複排除でもない。また `void fetchNotes();` は Promise を待たず戻り値を使わない意図を示すもので、例外を処理するのは内部の `try` / `catch` である。

### 普通の関数と `useCallback` の違い

**確認の出発点**

本人は「個人的にはsrc/modules/notes/notes.state.ts:9もsrc/modules/notes/notes.state.ts:10も同じ関数に見える」と質問した。当時その行にあった `getAll` と `set` は、どちらも普通のアロー関数だった。説明の訂正で以前の変更提案も変わるのか、という点も確認した。

**AI による補足**

`useCallback` は別の種類の関数を作る構文ではなく、React に関数を保持してもらう Hook である。呼び出す関数の処理内容を変えず、依存が同じなら前回と同じ関数を返す。

```ts
// 比較用の説明例。getAll の変更を提案したものではない。
const getAll = () => notes;

// 上の代わりに useCallback を使う場合
const cachedGetAll = useCallback(() => notes, [notes]);
```

| 描画 | 普通の関数 | `useCallback` で返される関数 |
| --- | --- | --- |
| 初回 | 関数A | 関数A |
| 依存が同じまま再描画 | 新しい関数B | 前の関数A |
| 依存が変わって再描画 | 新しい関数C | 新しい関数C |

会話前半の AI 説明「関数の作り直しを防ぐ」は厳密には不正確だった。新しい関数自体は作られるが、依存が変わらなければ React が前に保持した関数を返す、という訂正後の説明を採用する。`useCallback` は渡された関数をその場で実行せず、処理結果を保存するものでもない。

今回の提案は変更していない。store の `set` を `useCallback` で囲み、`Layout` はその関数だけを取り出して Effect の依存に入れる。`getAll` の例は比較説明であり、すべての関数を囲む提案ではない。

`useNoteStore` は再描画ごとに新しい戻り値オブジェクトを作る。`set` を安定させても `[noteStore]` を依存にしたままではオブジェクトの変化が残るので、`[currentUser, setNotes]` と組み合わせる。

### `useCallback` を使うか迷ったときの判断

**確認の出発点**

仕組みをどこまで覚えるべきか、初心者でも判断できる基準を確認した。

**AI による補足**

まず普通の関数で書き、「その関数が毎回変わると何が困るか」を確認する。全部の関数に付ける必要はない。

| 使い方 | 最初に選ぶ方法 |
| --- | --- |
| その場で呼ぶ、ボタンのクリックに渡すだけ | 普通の関数から始める |
| 1つの Effect 内だけで使う | Effect 内に定義する。今回の `fetchNotes` |
| Effect の外でも必要で、依存配列にも入る | 関数の参照が変わるかを確認し、必要なら `useCallback` を検討。今回の store の `set` |
| 最適化した子コンポーネントに渡す | 具体的な再描画コストを確認して検討 |

今回の問題は、Effect の状態更新 → 再描画 → 関数の参照変更 → Effect 再実行、という循環である。依存配列から必要な値を削除したり、理由なく `[]` にしたりして止めると、古い値を使い続ける原因になる。仕組みの細部を暗記するより、依存配列に関数があるときに定義場所を確認する習慣を付ける。

### Network で通信の繰り返しを確認する

**確認の出発点**

コードだけで発見する必要があるのか、ブラウザーのデバッグで確認できるのか、パフォーマンス測定が必要かを確認した。

**AI による補足**

同じ通信が続く問題なら、まず Chrome の Network で確認できる。いきなり性能測定を始める必要はない。

1. アプリを開き、Mac では `Command + Option + I` で開発者ツールを開く。
2. Network を選び、Fetch/XHR とフィルターの `notes` で対象を絞る。
3. ページを一度再読み込みし、その後は操作もコード保存もせず数秒待つ。
4. `/notes` が増え続けていないかを見る。`200` は成功であり、成功の繰り返しでも問題は起こり得る。
5. Initiator で通信を開始したコードをたどり、Effect の依存と状態更新を確認する。

開発時の StrictMode による初回の追加実行と、増え続けるループは区別する。通信件数だけで `useCallback` 不足と断定せず、定期取得など意図した動作も確認する。通信一覧は症状、依存配列と関数定義は原因を調べる手がかりである。

| 調べたいこと | 最初に使う機能 |
| --- | --- |
| 同じ API を何度も呼ぶか | Network |
| どのコードが実行されるか | Sources のブレークポイント |
| 描画・操作のどこに時間がかかるか | Performance や React Profiler |

初回整理時は手順の説明のみで、ブラウザーでの再現確認は未実施だった。後続の公開準備で行った AI の模擬API検証は、下記の追記に分けて記録する。本人が操作した結果とは扱わない。

### 関数のアルファベット順整列

ファイル内の関数を上から名前順に並べる候補として `eslint-plugin-perfectionist` の `sort-modules` を調査した。ファイル直下の関数宣言から限定的に試す案で、コンポーネント内部の Hooks や初期化式を無条件に並べ替える案ではない。
