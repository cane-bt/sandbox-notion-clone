## 確認したこと・理解の整理

### `interface` と `type` は今回どちらでも使える

**確認の出発点**

`NoteItem` の `interface` は何のためにあるのか。`type` との違い、世界的な好み、このリポジトリが採用している理由を確認したかった。

**AI による補足**

現在の定義は「`Note` 型の `note` を持つオブジェクト」を表す。

```ts
interface Props {
  note: Note;
}
```

今回の用途なら、次の `type` に置き換えても同じ役割を果たす。これは比較用の例で、実装は変更していない。

```ts
type Props = {
  note: Note;
};
```

どちらも型チェックのための定義であり、実行時のデータ検証を追加したり、画面の動作や再描画を変えたりするものではない。

| 比較 | `interface` | `type` |
| --- | --- | --- |
| オブジェクトの形を定義する | できる | できる |
| 文字列・数値などの型に別名を付ける | 直接はできない | できる |
| 「AまたはB」という型自体に名前を付ける | 直接はできない | `A \| B` でできる |
| 既存の型をもとに項目を追加する | 主に `extends` | 主に `&` |
| 同じスコープの同名宣言を統合する | できる | できない |

「`type` は拡張できない」という意味ではない。別の型と組み合わせることはできるが、同名の宣言を後から統合することはできない。`interface` の宣言統合は今回の `Props` では使っていない。

会話で確認したTypeScript公式は、多くの場合は好みで選べ、目安として `type` 特有の機能が必要になるまでは `interface` を使うと説明している。React公式はPropsに両方を認め、Googleのスタイルガイドはオブジェクトの型に `interface` を推奨している。ただし、推奨方針は利用者数の統計ではない。世界的な多数派を示す信頼できる統計は、今回の会話内の調査では確認できなかった。

リポジトリでは `SideBar/Item.tsx` や `ui/input.tsx` もPropsを `interface` で定義しており、周囲との一貫性はある。一方、確認したADR・README・ESLint設定からは、必ず `interface` を使うという採用理由や強制ルールは見つからなかった。作者の意図は断定しない。

「このリポジトリのPropsは周囲に合わせて `interface`、選択肢などの型には `type`」はAIの学習上の提案であり、新たに採用された規約ではない。

### `type` 特有の機能とは何か

**確認の出発点**

公式の目安に出てくる「`type` 特有の機能」が何を指すのかを確認したかった。

**AI による補足**

代表例はunion型に名前を付けること。`|` は「または」を表す。

```ts
type Status = 'loading' | 'success' | 'error';

const status: Status = 'loading'; // OK
// const status: Status = 'waiting'; // 型エラーになる例
```

ほかにも、既存の型の別名や、要素の型と順序が決まったtuple型を定義できる。

```ts
type NoteId = number;
type StringOrNumber = string | number;
type Coordinates = [number, number];
```

`NoteId` は別名なので、通常の `number` と区別される新しい種類の数値になるわけではない。

`interface` のプロパティにunion型を使うことはできる。項目に `|` を使うだけなら、Props全体を `type` に変える必要はない。

```ts
interface Props {
  note: Note;
  status: 'loading' | 'success' | 'error';
}
```

これらは説明用の例であり、現在の `Props` に `status` を追加したわけではない。

### `NoteItem({ note }: Props)` の読み方

**確認の出発点**

関数の引数にある `{ note }` と `: Props` をどう読めばよいかを確認したかった。

**AI による補足**

まず、分割代入を使わずに書くと次の形になる。処理を理解するための抜粋で、画面を返す部分は省略している。

```tsx
function NoteItem(props: Props) {
  const note = props.note;
}
```

`props` は受け取る変数名、`: Props` はその値の型指定。今回の実装は、引数を受け取る場所で直接 `note` を取り出している。

```tsx
function NoteItem({ note }: Props) {
  // 取り出した note を使う
}
```

- `{ note }`: 受け取ったオブジェクトから `note` を取り出す。
- `: Props`: 受け取るオブジェクト全体の型を指定する。
- 取り出した `note` 自体の型は、`Props` の定義にある `Note`。

`: Props` が `note` 自体の型を表している、と読まないことがポイント。

呼び出し側の `<NoteItem note={selectedNote} />` は、概念的には `{ note: selectedNote }` というPropsを渡している。左側の `note` はプロパティ名、`selectedNote` は渡す値であり、同じ変数名にする必要はない。

### 分割代入は必要な値を取り出す書き方

**確認の出発点**

本人の質問：「分割代入にはこういう書き方もあるという感覚で覚えておけばいいでしょうか。」

**AI による補足**

その感覚でよい。「オブジェクトから必要な値を取り出す書き方」として理解する。次の２つは今回の場合、同じように使える。

```ts
const note = props.note;
```

```ts
const { note } = props;
```

後者は `props` の `note` プロパティを取り出し、同じ名前の変数 `note` に入れる。値がオブジェクトなら、分割代入によってそのオブジェクトが複製されるわけではない。

複数の値も取り出せる。

```ts
const props = { note: '今日のメモ', title: 'ノート一覧' };
const { note, title } = props;
```

比較用の２通りを同じスコープに両方書くと `const note` が重複するため、例は別々に読む。引数での分割代入も同じ考え方で、今回のコードは「受け取ったPropsから `note` を取り出している」と読めればよい。
