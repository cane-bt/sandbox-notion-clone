### `newNote` の型エラーと `key` の警告

**対象ファイル・箇所**

[src/components/NoteList/index.tsx](../src/components/NoteList/index.tsx) の `createChild`。関連する戻り値は [src/modules/notes/note.repository.ts](../src/modules/notes/note.repository.ts) の `create`、受け取り側は [src/modules/notes/notes.state.ts](../src/modules/notes/notes.state.ts) の `set`。

**確認の出発点**

質問時点の13行目で `newNote` がエラー扱いになり、ブラウザーには `Each child in a list should have a unique "key" prop.` と表示された。講座では作成できているように見えるため、原因を確認したかった。

**AI による補足**

質問時点では `noteRepository.create({ parentId })` の前に `await` がなかった。`create` の戻り値は `Promise<Note>` なので、変数に入るのはノート本体ではなく、後から結果を受け取るための Promise。`Note[]` を要求する `noteStore.set([newNote])` に渡すと型が合わない。

```tsx
const newNote = await noteRepository.create({ parentId });
noteStore.set([newNote]);
```

`async` を外側の関数に付けるだけでは、中の処理を自動で待たない。`await` で作成結果の `Note` を受け取ってから store に追加する。

型エラーがあるまま実行すると、Promise が store に入り得る。Promise にはノートの `id` がなく、一覧の `key={note.id}` が `undefined` になるため、今回の警告につながる。`key` の記述自体は既にあったため、追加するだけでは解決しない。

`await` がなくても API リクエスト自体は開始されるため、サーバー側でノートが作成されている可能性はある。講座のコードやサーバー側の結果は未確認で、環境差とは断定しない。修正後は再読み込みして、store に残った不正な値を解消してから確認する。整理時点のコードには `await` が追加済みだが、この整理作業では実通信を検証していない。

### マウスイベントの型と `preventDefault`

**対象ファイル・箇所**

[src/components/NoteList/index.tsx](../src/components/NoteList/index.tsx) の `createChild` の引数と `e.preventDefault()`。クリック元は [src/components/NoteList/NoteItem.tsx](../src/components/NoteList/NoteItem.tsx) の「＋」を含む `div`。

**確認の出発点**

`e: React.MouseEvent` を初めて見たので意味を確認したかった。続けて、`React.MouseEvent` と `e.preventDefault()` は、まず役割を覚えておけばよいかを確認した。

**AI による補足**

TypeScript の `引数名: 型` という書き方で、`e` は引数名、`React.MouseEvent` は React のマウスイベントを表す型。`e` は慣習的な省略名で、`event` でもよい。型指定そのものがイベントを作るわけではない。

React がクリック時に渡すイベントには、座標を示す `clientX` や Shift キーの状態を示す `shiftKey` などの情報と、操作に関係するメソッドがある。

- `e.preventDefault()` はリンク先への移動など、ブラウザー標準の動作を止める。
- `e.stopPropagation()` は親要素などへのイベントの伝達を止める。役割が異なる。
- クリック処理に `preventDefault()` が常に必要なわけではない。現在のクリック元は `div` なので、通常は止めるべき標準動作がなく、必須ではない。

今は「イベントを受け取るための型」「標準動作を止めたいときのメソッド」という役割を押さえ、必要な場面で調べられればよい、という説明をした。これは本人が理解済みと申告した記録ではない。

### `NoteList` と `NoteItem` の関係と実行順

**対象ファイル・箇所**

[src/components/NoteList/index.tsx](../src/components/NoteList/index.tsx) の `NoteList`・`createChild` と、[src/components/NoteList/NoteItem.tsx](../src/components/NoteList/NoteItem.tsx) の `Props.onCreate`・`NoteItem`・`onClick`。最初の質問では、前者の9行目と後者の20行目が指定された。

**確認の出発点**

2つの関数・型の関係、続いて両ファイル全体の役割と処理の流れを確認したかった。同じ対象への再質問はこの節へ統合した。

**AI による補足**

親の `NoteList` は一覧と作成処理を担当し、子の `NoteItem` はノート1件の表示と操作の受け付けを担当する。親は `noteStore.getAll()` で store の配列を読み、各ノートについて `NoteItem` を表示する。`getAll()` 自体は API 通信ではない。

```tsx
<NoteItem
  key={note.id}
  note={note}
  onCreate={(e) => createChild(e, note.id)}
/>
```

`note` は表示するデータ、`onCreate` は子が呼ぶ関数。`key` は React 用の識別情報で、通常の props として子から読み取る値ではない。

子の型宣言は、処理の実行ではなく「何を受け取れるか」の定義である。

```tsx
interface Props {
  note: Note;
  onCreate?: (event: React.MouseEvent) => void;
}
```

`?` は省略可能、`(event: React.MouseEvent)` はイベントを1つ受け取ること、`=> void` は呼び出す側が戻り値を使わないことを表す。`event` と親の `e` は名前が違ってもよい。`async` 関数の失敗が型宣言によって自動処理されるわけではなく、作成処理側の `catch` が必要。

`NoteItem({ note, onCreate }: Props)` は props から2つの値を取り出す。子は `note.title ?? '無題'` を表示し、右側のメニューにある「＋」の `onClick` に `onCreate` を設定する。`??` の代替値は `null` または `undefined` のときに使われる。

```text
親が表示するノートと関数を子へ渡す（まだ作成しない）
→ ユーザーが「＋」をクリック
→ React がイベントを渡して onCreate を呼ぶ
→ (e) => createChild(e, note.id) が動く
→ createChild にイベントと親ノートの ID が渡る
→ API の作成結果を await で待つ
→ noteStore.set([newNote]) で共有状態へ追加する
→ NoteList が再描画され、更新された配列から NoteItem を表示する
```

`onCreate` はアプリで付けた名前、`onClick` は React のクリック処理用の props。`onCreate` という名前だけで自動実行されるわけではなく、子の `onClick={onCreate}` で接続している。

親から渡す `(e) => createChild(e, note.id)` がノートの ID を付け加えるので、子はイベント1つを渡すだけでよい。たとえば ID が `10` のノートなら `createChild(e, 10)` が呼ばれる。関数を渡して必要なタイミングで呼んでもらう書き方をコールバックと呼ぶ。

### React のリスト表示で覚える基本

**対象ファイル・箇所**

[src/components/NoteList/index.tsx](../src/components/NoteList/index.tsx) の `notes.map()` と `key={note.id}`。

**確認の出発点**

このファイルの書き方は、React でリストを表示する際に推奨されるものなのかを確認したかった。

**AI による補足**

「配列を用意する → `map()` で各要素を JSX に変換する → 安定した一意の `key` を付ける」は React 公式でも紹介される基本。`key` には同じ一覧内で重複せず、再描画で変わらない ID を使う。追加・削除のある一覧で配列の位置を識別子にすることは避けたい。

今回のように1件にタイトル・メニュー・ボタンがある場合、`NoteItem` へ分けると役割を読み取りやすい。ただし分割は必須ではなく、単純なリストは `map()` 内に直接 `li` などを書いてもよい。

`useNoteStore()`、`noteRepository.create()`、`onCreate` はこのアプリで定義した仕組みであり、React の一覧表示に必須の API ではない。`index.tsx` というファイル名も React が指定するものではない。ファイル全体を固定テンプレートとして暗記する必要はない。

### cleanup を渡す時点と実行される時点の復習

**対象ファイル・箇所**

[_TIL/2026-11-07(Sat).md](2026-11-07%28Sat%29.md#cleanup-を渡す時点と実行される時点) の「cleanup を渡す時点と実行される時点」。本人が示した対象は TIL 内の説明用コードであり、現在のアプリ実装そのものへの質問とは区別する。

**確認の出発点**

以下のコードについて、実行順と考慮すべきことを含めてもう一度説明してほしいという質問だった。

**AI による補足**

```tsx
useEffect(() => {
  if (!currentUser) return;
  let ignore = false;

  const fetchNotes = async () => {
    const notes = await noteRepository.find();
    if (!ignore) {
      setNotes(notes);
    }
  };

  void fetchNotes();

  return () => {
    ignore = true;
  };
}, [currentUser, setNotes]);
```

これは仕組みを絞った説明用コードで、エラー処理等を省略している。

1. React が Effect の setup を実行する。初回のマウント後、または依存値が変わった更新後が対象になる。
2. `currentUser` がなければ終了する。この実行では通信も cleanup の返却もしない。以前の実行の cleanup があれば、新しい setup の前に実行される。
3. 今回の実行専用の `ignore` を `false` にする。普通の変数なので、変更だけでは再描画しない。
4. `fetchNotes` を定義する。この段階ではまだ実行していない。
5. `void fetchNotes();` で関数を実行する。`find()` が通信を開始し、`fetchNotes` の続きは `await` で待機する。
6. 外側の setup は待機せず先に進み、cleanup 関数を React に返して終了する。ここで `ignore = true` が実行されるわけではない。
7. 通信が成功すると `await` の後から再開し、その時点の `ignore` を確認して結果を反映するか判断する。

関数を返すことと呼び出すことは別である。

```tsx
const cleanup = () => {
  ignore = true;
};
return cleanup; // 関数を渡す。cleanup() と呼んだわけではない
```

| 通信完了と cleanup の順番 | 結果 |
| --- | --- |
| cleanup より先に通信が完了 | `ignore` は `false` なので `setNotes(notes)` を実行する |
| 通信中に cleanup が実行され、その後に通信が完了 | `ignore` は `true` なので結果を反映しない |

cleanup は通信完了をきっかけに動くのではない。コンポーネントが取り除かれたとき、または依存変更に伴って次の setup を行う前に React が呼ぶ。依存値が変わらない通常の再描画だけではやり直さない。開発時の StrictMode では追加の setup → cleanup → setup が行われる場合がある。

`fetchNotes` と cleanup は同じ実行の `ignore` を参照するため、待機中の変更を後から確認できる。外側の変数を関数から参照できる仕組みが closure。次の Effect 実行には別の `ignore` が作られるので、古い実行のものが `true` でも新しい実行は `false` で始まる。

考慮する点:

- cleanup の `ignore = true` は通信を中止しない。通信後の `if (!ignore)` と組み合わせて不要な結果の反映を防ぐ。通信のキャンセルや重複排除は別の仕組み。
- cleanup 前に反映済みのデータは取り消さない。ログアウト時の既存データの消去も別に必要。
- `void` は Promise を待たず戻り値を使わない意図を示すだけで、例外を処理しない。失敗への対応は `try...catch` 等で行う。
- エラー表示や読み込み状態の更新を加える場合も、古い処理の結果を反映しないか確認する。
- 依存配列の値は参照も含めて比較される。オブジェクトや関数を毎回作り直すと、内容が同じでも Effect をやり直す原因になる。
