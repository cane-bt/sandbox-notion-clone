### ID でノートを検索する `getOne`

**対象ファイル・箇所**

[src/modules/notes/notes.state.ts](../src/modules/notes/notes.state.ts) の `useNoteStore` 内の `getOne`（質問時点の12行目）。

**確認の出発点**

本人から、この1行を初心者向けに詳しく説明してほしいという質問があった。

**AI による補足**

```ts
const getOne = (id: number) => notes.find((note) => note.id === id);
```

`getOne` は数値の `id` を受け取り、現在の `notes` 配列から ID が一致する最初のノートを返す関数。定義しただけでは検索せず、`getOne(3)` のように呼んだときに実行する。

- `id: number` は TypeScript の型指定。文字列を数値へ変換する処理ではない。
- 外側のアロー関数は ID を受け取る。内側の `(note) => note.id === id` は、`find` が各要素について呼ぶコールバック。
- `note` は今調べている1件、`note.id` はその ID、右辺の `id` は検索したい ID。`===` は型変換せず一致を比較する。
- 内側の関数が返すのは `true` または `false`。`find` が返すのは条件に一致したノートそのもの。一致がなければ `undefined`。
- `=>` の後に波括弧を付けず式を書くと、その式の結果を返す。これが暗黙の `return`。

省略を展開すると次の意味になる。

```ts
const getOne = (id: number) => {
  return notes.find((note) => {
    return note.id === id;
  });
};
```

例えば ID が `1`、`3`、`5` の順で並ぶ配列に対し `getOne(3)` を呼ぶと、`1` は不一致、`3` で一致して検索が終わる。ID だけでなくノート全体を返す。`getOne(99)` は `undefined` になる。

戻り値の型は `Note | undefined`。呼び出し側では見つからない場合を考慮する。配列を書き換えず、API に取得しに行く処理も含まない。初期状態の空配列を検索すれば `undefined` になる。整理時点の `NoteDetail` には `if (!note)` の表示分岐があるが、その実行結果は未検証。

### `noteStore` と `notesStore` の命名

**対象ファイル・箇所**

[src/pages/NoteDetail.tsx](../src/pages/NoteDetail.tsx) の `NoteDetail`（質問時点の14行目の参照、宣言は13行目）と、[src/modules/notes/notes.state.ts](../src/modules/notes/notes.state.ts) の `useNoteStore`。

**確認の出発点**

本人から、単数形と複数形のどちらが適切か、それぞれの理由とベストプラクティスについて質問があった。

**AI による補足**

```ts
const noteStore = useNoteStore();
const note = noteStore.getOne(id);
const notes = noteStore.getAll();
```

`note` は1件のノート、`notes` は配列、`noteStore` は `getAll`・`getOne`・`set` を持つ操作用オブジェクトであり、同じものではない。

`noteStore` の `note` は「ノートという種類のデータを扱う」という修飾で、1件しか管理しないという意味ではない。書店の `bookStore` が複数の本を扱うのと似ている。

`notesStore` は「ノートの集合を管理する」ことを強調する命名で、こちらも意味が通る。どちらも `Store` 自体は単数で、`noteStores` なら複数の Store を表す別の名前になる。

実用的な判断基準は、データ自体の1件と複数件を区別し、管理オブジェクトには役割を表す名前を付け、既存コードと一貫させること。配列に複数形を使う指針を、配列を内部で扱うすべての管理オブジェクトへ機械的に適用しない。

このプロジェクトでは `useNoteStore`、`noteRepository`、他のコンポーネントの `noteStore` と揃うため、AI は現状の `noteStore` を維持することを勧めた。これは命名の説明・推奨であり、新しい運用方針を採用したという記録ではない。

### スコープと `return` を踏まえた画面遷移の位置

**対象ファイル・箇所**

[src/components/NoteList/index.tsx](../src/components/NoteList/index.tsx) の `createChild`、`setExpanded` のコールバック、`moveToDetail`。質問時点の35行目と29行目が対象。

**確認の出発点**

本人は35行目のエラーに対応するため29行目へ同じコードを書くことを試し、その直前の `return` によって期待どおり動かないのではないかと疑問を持った。

**AI による補足**

問題は2つに分かれる。

1. `newNote` は `try` の内側で `const` 宣言されているため、外側から参照できない。これがスコープの問題。さらに `catch` の後では作成失敗時にも遷移処理へ進んでしまう。
2. `setExpanded` のコールバック内の `return newExpanded` より後へ書いても、その処理は実行されない。値が返らないのではなく、値を返してそのコールバックが終了するため。

この `return` は外側の `createChild` 全体を終了させない。そのため、`setExpanded(...)` の後、かつ `try` の中へ遷移処理を書く。

```tsx
try {
  const newNote = await noteRepository.create({ parentId });
  noteStore.set([newNote]);
  setExpanded((prev) => {
    const newExpanded = new Map(prev);
    newExpanded.set(parentId, true);
    return newExpanded;
  });
  moveToDetail(newNote.id);
} catch {
  alert('ノートの作成に失敗しました');
}
```

処理は「作成を待つ → Store へ追加 → 親を展開する state 更新を予約 → 詳細画面へ移動」の順になる。`setExpanded` は画面の更新完了を待つ処理ではない。

コールバックの `return` より前に遷移処理を移す方法も避ける。state 更新用のコールバックは、前の state から次の state を計算して返す役割とし、画面遷移は外で行う。

2026-11-20 の整理時点では、作業ファイルが上記の位置関係へ修正されていることを確認した。TIL 整理のためにアプリのコードは編集しておらず、ブラウザでの成功・失敗の動作確認も実施していない。
