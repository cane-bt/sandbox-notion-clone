## 確認したこと・理解の整理

### 入力通知と保存完了

**対象ファイル・箇所**　[`src/pages/NoteDetail.tsx`](../src/pages/NoteDetail.tsx) の `NoteDetailContent` と [`src/components/TitleInput.tsx`](../src/components/TitleInput.tsx) の `TitleInput`

**確認の出発点**　教材のようにタイトルを遅延保存すると、旧来の `onSave={debouncedTitle}` でなぜ型エラーになるか。

**AI による補足**　教材画像ではタイトル変更時に `updateNote(id, { title })` を呼んでいる。手元の `updateNote` は親のスコープにある `id` を使う。元の `onSave` は毎回 `Promise<void>` が返ることを要求するが、debounce された関数は初回の予約時に `undefined` を返し得る。直接 `saveTitle` を渡す案はフォーカスを外した時点で保存したい場合に使える。遅延保存を選んだ現在の実装では、子が受け取る型を `(title: string) => void` としている。子は通知の戻り値を使わず、親では引き続き非同期関数 `saveTitle` が通信の完了を待つ。

### 入力時と再試行時の呼び分け

**対象ファイル・箇所**　[`src/components/TitleInput.tsx`](../src/components/TitleInput.tsx) の `TitleInput` と [`src/pages/NoteDetail.tsx`](../src/pages/NoteDetail.tsx) の `debouncedTitle`・`saveTitle`

**確認の出発点**　なぜ `onBlur` を外すのか。`onRetry` は標準機能か。再試行ボタンのエラーを直すには関数の引数も変えるのか。

**AI による補足**　親は `onTitleChange={debouncedTitle}` と `onRetry={saveTitle}` を渡す。子は両方を引数で分割代入する。`Props` に書くだけでは関数内に同名の変数はできない。入力時は `setValue(title)` で表示をすぐ更新し、続いて `onTitleChange(title)` で保存を予約する。再試行ボタンの `onClick` からは旧名の `onSave` を外し、独自の prop である `onRetry(value)` を呼んで即時保存する。

この方式では、元の `onBlur` でも直接保存すると、予約中の保存と重なる可能性がある。欄を離れたらすぐ保存したい場合は、親で `debouncedTitle.flush()` を呼ぶ方法もある。これは会話で扱った別案。

### 検索の待ち時間

**対象ファイル・箇所**　[`src/components/SearchModal.tsx`](../src/components/SearchModal.tsx) の `SearchModal`

**確認の出発点**　検索 API の呼び出しには何ミリ秒が適切か。

**AI による補足**　11月27日のコードでは `useDebouncedCallback(onKeywordChange, 500)` を使う。100ms間隔で「n」「no」「not」と入力すると、そのたびにタイマーが更新され、最後の「not」から500ms後に検索を依頼する。入力中に500msごとに繰り返す動作とは異なる。検索候補の応答性を優先するなら、会話で紹介した Algolia の200msは試し始める目安になる。API 応答に150msかかれば、200ms待つ設定でも結果が届くまで約350msかかる。実際のリクエスト数と表示までの時間を見て決める。

### タイトル保存後のフォーカス

**対象ファイル・箇所**　[`src/pages/NoteDetail.tsx`](../src/pages/NoteDetail.tsx) の `saveTitle`・`saveContent`、[`src/components/TitleInput.tsx`](../src/components/TitleInput.tsx) の `TitleInput`、[`src/components/Editor.tsx`](../src/components/Editor.tsx) の `Editor`

**確認の出発点**　タイトル保存時だけ入力欄からフォーカスが外れるのはなぜか。保存後に戻せるか。

**AI による補足**　両方とも500ms待ってから保存する。違いは、タイトル保存では `setIsSaving(true)` によりタイトル欄が無効になる点。本文のエディタは本文保存中も入力可能なまま。タイトル欄を再び有効にするだけでは、元のフォーカスは自動で戻らない。

変更後の `TitleInput` は、`inputRef` に実際のテキストエリアを保持する。`useLayoutEffect` 内で、無効化の直前に `document.activeElement === input` を確認し、その結果を `restoreFocus.current` に記録してから `input.disabled = isSaving` を実行する。保存終了時は先に入力可能に戻し、次節の条件を満たせばフォーカスを戻して記録をリセットする。

### フォーカス先の読み方

**対象ファイル・箇所**　[`src/components/TitleInput.tsx`](../src/components/TitleInput.tsx) の `TitleInput` 内の `useLayoutEffect`

**確認の出発点**　各 DOM API の役割は何か。JavaScript 標準の関数なのか。ページ本体との比較で何が分かるか。

**AI による補足**　`document.activeElement` はページ内のフォーカス先を読むプロパティ。`document.hasFocus()` はページ自体がフォーカスを持つかを返すメソッド。どちらもブラウザが提供する DOM API で、React は不要。たとえばアドレスバーに移動すると、ページ内の最後の要素が `activeElement` に残っていても、`hasFocus()` は `false` になる。

`document.activeElement === document.body` は、フォーカス先が `<body>` そのものかを調べる。本文エディタもボタンもその内側にあるが、それぞれ別の要素なので比較結果は `false`。タイトル欄が無効になり、他にフォーカス先がなければ、通常は `<body>` が返る。この比較で分かるのは確認した瞬間の状態であり、余白をクリックしたかどうかまでは分からない。

保存前はタイトル欄にいて、現在は `<body>` がフォーカス先で、かつページ自体にフォーカスがあるときだけ `input.focus({ preventScroll: true })` を呼ぶ。これで画面を自動スクロールさせずにタイトル入力を再開できる。保存中に本文へ移っていれば、その入力を続けられる。

### スプレッドシートの自動保存は何秒か

**対象ファイル・箇所**　Google スプレッドシートのセル編集。手元の比較対象は [`src/pages/NoteDetail.tsx`](../src/pages/NoteDetail.tsx) の `debouncedTitle` と `saveTitle`。

**確認の出発点**　「個人的にはこの教材の学習で学んだ内容より、遅いような気がします。」同じ疑問を持った利用者にどんな回答があり、Sheets の debounce の長さをどこまで推定できるかを調べた。

**AI による補足**　Google は、セルの外をクリックして入力を確定する操作と、変更をブラウザに保存してから Google に送信する流れを説明している。今回確認した公式資料では、最後の入力から送信までに固定の debounce を設けているか、その時間が何msかは未確認。[Google 公式ヘルプの保存操作](https://support.google.com/docs/answer/49114?hl=ja)・[ブラウザでの保存と送信](https://support.google.com/docs/answer/11468464?hl=ja)

ヘルプコミュニティでは、Sheets の自動保存設定を尋ねた人に「編集のたびに保存される」という趣旨の回答があった。別の編集ツール全般の質問には、接続が良好なら数秒おきという回答もある。前者は保存対象となる編集、後者は利用者から見た時間の目安を説明している。どちらの投稿にも、現行の Sheets でセル確定から最初の送信までを計測した値は示されていない。[自動保存設定についての質問](https://support.google.com/docs/thread/268389251/autosave-settings?hl=en)・[保存頻度についての回答](https://support.google.com/docs/thread/305780479/how-do-i-save?hl=en)

手元の `500ms` は、最後の入力から `saveTitle` を呼ぶまでの待ち時間。仮に保存 API の応答にさらに800msかかると、入力から完了までは約1.3秒になる。Sheets でも「保存済み」の表示までを体感しているなら、500msより長く感じることは説明できる。これは時間の区間を比べた推論で、Sheets の内部タイマーの実測値は得られていない。
